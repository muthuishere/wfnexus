## 1. Mastra, and the claims it killed

Mastra was under-weighted as "a trace waterfall we should copy for UX". It is the strongest
counterexample in the whole survey to what we were claiming.

Verified from [their docs](https://mastra.ai/docs/workflows/overview):

| what they have | what it costs us |
|---|---|
| `createStep()` with **input and output schemas** (Standard JSON Schema — Zod, Valibot, ArkType), TS type inference through `getWorkflow()` **plus** runtime validation | "typed hand-off" is not ours as a category |
| **agents can be steps**; steps call registered agents or execute tools | "typed hand-off between two *agent* steps" is narrower than we thought |
| tools per agent **and per call** — `activeTools` / `toolChoice` / `toolsets` / `clientTools` at `.generate()` time | per-step scoping is not ours, and theirs is *dynamic* where ours is a static allowlist |
| `beforeToolCall` hook returning `{ proceed: false, output }`; documented example blocks `rm -rf` | our `guardrails: deny + args_contain` is the same mechanism with the same worked example |
| **`mastra lint`** — static, `--strict`, `--json`, `--preflight`, no model calls | "nobody ships a real static validation pass" is **false as written** |
| `mastra worker build/start`, `mastra env` (+ managed Turso/Neon), `mastra auth`, `mastra scorers`, OTEL by default, `mastra factory dev` (Agent Builder) | most of our roadmap, already released, plus evals and OTEL which were not on ours |

**Unverified:** the exact rule set `mastra lint` applies — the reference page 404s on both URL forms.
So *whether* it checks graph/schema compatibility is unknown; *that it is a static pass* is not.

Two corrections to make in our own words:

- The "nobody has a static pass" line was true of the **canvas tier** (6/6 test by really running)
  and we generalised it to everyone. Mastra is not in that tier and has one.
- For typed edges specifically, **`tsc` is a stronger check than `wfx dryrun`** — it fails the build
  rather than a command you have to remember to run.

### What Mastra is not

A library you write TypeScript in, deployed to **their** platform (`mastra deploy` → Mastra platform
environments, managed DBs). Executor free and self-hostable, money on the control plane — which is
exactly the rule our own research derived from Earthly's corpse. They are playing it correctly.

They have no repository model: no worktree, no working tree, no PR, and nothing runs before
`mastra build` in a Node project.

## 2. What we are, restated

The old pitch argued on the authoring axis — our YAML vs their TypeScript. That is a fight against a
funded framework with a better Studio, and on the evidence we lose it. Two moves take us off that
axis.

### 2.1 Nobody writes the YAML

The workflow is **generated** by an agent skill running inside whatever the author already uses —
Claude Code, Codex, opencode. The YAML stops being an authoring surface and becomes the **receipt**:
readable, diffable, committable, reviewable by someone who never touched the generator. Mastra's
artifact is a TS module inside a bundler project; you cannot hand that to a reviewer as evidence.

This makes the dry run load-bearing instead of a footnote. The generator already does
generate → statically prove → repair, with **no model call in the verification half**. `mastra lint`
and `tsc` check code a human wrote; neither can close a generation loop against a workflow that does
not exist yet.

### 2.2 The execution backend is a swappable detail

This is the novel claim, and it is the one to build on. Observed in a real boot on this machine:

```
claude-cli   cli    ~/.local/bin/claude
copilot-cli  cli    /opt/homebrew/bin/copilot
devin        acp    /opt/homebrew/bin/devin
opencode     cli    openrouter/anthropic/claude-haiku-4.5
gpt / haiku / sonnet   http   openrouter
```

CLI agents, an ACP agent and raw HTTP models behind **one step declaration**. The same
`prompt + skills + tools + output_schema` runs on any of them, and toolnexus (ADR 0001) is what makes
them interchangeable — which is why the Go/toolnexus foundation is the reason the claim exists, not
an implementation note.

Everyone else ships **a runtime you must live inside**: Mastra binds you to their TS runtime,
gh-aw to GitHub + Copilot, Devin and Jules are their own model. We ship **a unit that travels**.

**Build once in Claude. Publish it with its skills and MCP. Run it against Codex, opencode, or your
own API, on your own machine.**

### 2.3 The cost of that claim

Portability is only true if a workflow that passes on sonnet also passes on opencode. The contract
gate helps — `submit_output` validates identically on every backend — but *capability* differs.

So **evals stop being a gap we skipped and become the proof of the core claim.** You cannot sell
"runs anywhere" without showing it still passes there. The one thing Mastra has that we do not is
now load-bearing rather than optional.

## 3. The shape of the product

A **self-hosted registry and runtime for agent assets**. Author anywhere; publish skills, MCP
servers, workflows and templates to **your own** registry; run them on your own machines.

The architecture already anticipated this — ADR 0011 is literally *one registry type for everything a
step names*, and the server boots by loading skills from three roots (86 of them), `mcp.json`,
`registries.json` (7 providers, 4 classifiers) and `templates/`. What is missing is the **publish
direction**: today every one of those is read from disk and nothing can be pushed.

Nobody has this. npm and OCI registries exist for code and images; `npx skills add` is a *public*
installer with no private registry and no runtime. A self-hostable registry for agent assets with a
typed runtime attached is unoccupied ground.

### Client and identity

- `wfx login --url https://wfx.example.com` — **OAuth 2.0 device authorization grant (RFC 8628)**,
  the flow `gh auth login`, Docker and the AWS CLI use. No localhost callback, so it works over SSH,
  in a container, and **inside someone else's agent session** — which is the point when authoring
  happens in their Claude or Codex. Do not invent this.
- `wfx logout`; multiple hosts as named contexts (`gh auth login --hostname` / `kubectl config` /
  `docker login <registry>`). Host-agnostic by construction, so "host it wherever" is another context.
- Precedent exists: workers already join with `wfx_…` tokens. This extends a token model rather than
  adding a subsystem.

### Authorization

Local users and roles first, default admin, both editable. Authentication is pluggable later (OIDC,
LDAP); **authorization is ours, permanently**, and project-scoped from day one because projects
already exist in the schema.

### The UX rule

**Extremely simple.** The run is the hero, drawn as time. Not an inventory table.

## 4. What one live run proved, 2026-09-24

`code-review` against this repo, `main~3..main`, sonnet-4.5 via OpenRouter. Let it cost, on purpose.

**Worked:**

- `wfx dryrun` printed waves, per-step budgets and `ceiling: 50 model turns across 2 agent step(s)`
  instantly, for nothing, and said `would run.`
- Bad input was refused **before a run row existed** — Trigger.dev's "schema failures are not
  retryable" rule, already implemented and not written down anywhere.
- Per-run git worktree, guardrails, scoped skills/tools all engaged as declared.
- **The run completed**: `survey` 4 turns, `review` 27 turns, both with validated typed output
  (`survey` → `areas`, `files_changed`, `has_tests`, `summary`). 31 LLM calls, 30 tool calls.

**Defects found, all real, none previously recorded:**

| defect | evidence | why it matters |
|---|---|---|
| **A running step reports no progress.** `turns` is written only when a step ends | `review` showed `turns=0` after 29 LLM calls, then `27` the instant it finished | the "what is this agent doing right now" screen is not supported by the data model |
| **No cost anywhere.** `MetricEvent` carries prompt/completion tokens per call and is thrown into the event log | computed **$4.37** for this run by hand from events the platform already emits | the one number a local runtime can show that a hosted product cannot, and it is uncomputed |
| **No context compaction** | **1,424,154 prompt tokens against 6,541 completion** — the 117 KB diff re-sent every turn | already the #1 unused toolnexus capability; here it is as money |
| **POST and GET disagree on the envelope** | `POST /runs` returns the run flat; `GET /runs/{id}` nests it under `run` | it misled me writing a client in this session; it will mislead everyone else |
| **Boot prints ~40 duplicate-skill warnings, twice** | first screen a new user sees | violates "extremely simple" before the product starts |
| **`bash` tool calls display with `WFX_*` exports inlined** | every `tool_call` event's `args.command` | the command shown to a human is not the command they would read |

**Distribution, checked:** remote is `git@github.com:muthuishere/wfnexus.git` and the module is
`github.com/muthuishere/wfnexus/apps/api` — so the rename the ROADMAP lists as pending is **done**,
and that entry is stale. But there are **no git tags, no `.github/workflows`, no goreleaser, no npm
package and no brew tap**. `task release` builds 18 binaries onto one disk and publishes nothing.
Nobody can get `wfx`. That is now a headline problem, because under this pivot the client *is* the
product surface.

## 5. Order of work

1. **Distribution.** Tag, CI, and one install line. The client is the product and it is unobtainable.
2. **Login → publish → registry.** `login` first despite "skill first", because publish needs an
   identity to publish *as*. Device flow, then `wfx publish` for skills / MCP / workflows.
3. **The run view, and the cost.** Spans, durations, tokens, one attempt = one span (Inngest), and
   `$` computed from the metrics we already emit and discard. Fix the running-step `turns` write
   first or the screen cannot be built.
4. **Evals.** Promoted from "gap we skipped" to the proof of the portability claim.
5. **Auth and authorization** as in §3.
6. **Compaction.** The cost finding makes this a money problem, not a capability problem.

Everything else on the previous adopt list — memoised `--recover`, effects, pinning, actionlint —
still good, still cheap, and none of it changes whether someone picks this over Mastra.

## 7. Kill criteria

The defensible surface is **portability across execution backends** plus **generation with a
zero-token static proof**. If Mastra ships a provider abstraction that runs a workflow on a local
CLI agent, or gh-aw ships `needs:` with typed outputs between agentic jobs, the honest move is to
stop building a platform and ship the `submit_output` contract gate as a library that plugs into
theirs.
